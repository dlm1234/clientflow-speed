# Supabase setup — manual handoff

Use a dedicated project with no real customer records for evaluator access. If your approved project already has the migration, do not create another project or reapply it.

1. In the [Supabase dashboard](https://supabase.com/dashboard), create a project on a Free organization, choose a region and generate a database password. Store the password separately; do not put it in ClientFlow. Check [current plan limits](https://supabase.com/pricing) before confirming.
2. On a fresh project only, open its SQL Editor, paste the contents of [the workspace migration](../supabase/migrations/20261125000000_clientflow_workspace.sql), and run it once against that new project. It commits as one transaction. Do not run it against an existing production database or mix manual application with a subsequent migration push of the same file.
3. In **Authentication → Providers**, verify that Email sign-in, sign-ups and email confirmation are enabled, and anonymous sign-in is disabled. Verify the configured minimum password length is compatible with the app’s eight-character minimum. In **Authentication → URL Configuration**, verify **Site URL** is `http://127.0.0.1:3000` and **Redirect URLs** contains exactly `http://127.0.0.1:3000/auth/confirm` for local development (no wildcard). Change remote settings only with separate permission.
4. Leave **Confirm signup** on the standard Supabase template and keep confirmation enabled. The signup action sends the callback explicitly. The intended flow verifies the email, then exchanges the PKCE code with the original profile's verifier cookie for an SSR session. In the reported hosted test, automatic session establishment did not work; a confirmed user can instead sign in with their password. See [PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow) and [exact redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).
5. Set `APP_ORIGIN=http://127.0.0.1:3000` in the existing ignored `.env.local`; do not overwrite it. For a fresh checkout, use `.env.example` as a template. The Supabase API URL and publishable key go under `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Do not use secret/service-role/database credentials. `APP_ORIGIN` is read on the server and must be an origin, not a callback path; HTTPS is required except for loopback. A missing or invalid origin blocks signup without disabling ordinary login. The existing token-hash callback remains compatible with links issued under the previously documented custom template; new signups do not require it.
6. Run `npm ci --ignore-scripts` if needed, then `npm run dev`; open `http://127.0.0.1:3000`, not `localhost`. Restart the server when its environment changes.

## Real confirmation with two users — after a separate approval

1. Verify eligibility for both distinct inboxes before starting. The [default sender](https://supabase.com/docs/guides/auth/testing-auth-flows) delivers to pre-authorized team addresses only and is limited to two Auth emails per hour for the entire project, shared with resends and other flows. Do not add team members, resend repeatedly, or disable confirmation to work around delivery. Report a missing inbox or rate limit as BLOCKED.
2. Use separate browser profiles A and B. In A register account A at `/registro`; expect a prompt to check email and verify that protected routes redirect before confirmation. Open the email’s standard link in the **same profile and origin** that started signup. Do not share the link or copy callback parameters into evidence.
3. Check that confirmation took place separately from the app session. A successful session lands at a clean `/dashboard` and can reload the Dashboard, Clientes and Proyectos. A different browser, cleared cookies or an expired code cannot complete automatic login; if the account is already confirmed, sign in at `/login` with its password. That fallback is not a PKCE success.
4. Sign out, reload a protected route and confirm it redirects to login. Repeat sequentially for B within the shared mail budget. Keep only statuses and timestamps, not addresses, credentials, cookies, links or tokens. Local mocked tests do not prove these outcomes.

## Vercel handoff — no deployment performed

Use the stable HTTPS deployment origin as `APP_ORIGIN` to mark server-written session and verifier cookies Secure, and authorize that exact `/auth/confirm` URL in Supabase. Do not construct it from request headers or add wildcard preview domains for this exercise. Start and finish each registration on the same hostname. Verify that platform access logs and any log drains do not retain callback query parameters; Next.js local logging configuration cannot control platform logs. Hosted mail limitations still apply on Vercel: external reviewers generally need separately authorized custom SMTP if their addresses are not already eligible. Verify the sender, domain and actual quota/cost before claiming that setup is free. Do not change mail or deployment configuration as part of the local check.

## Hosted authorization checks — after separate permission

After both accounts are confirmed, use only ordinary user sessions and disposable run-scoped records; no service role. In separate browser profiles, create a client and a project with each account, verify persistence after reload, and confirm that neither profile lists the other owner's records. Under the separately authorized verification plan, check the same owner/non-owner permissions through the Data API with the publishable key and each account's own session. Confirm denied writes did not change the owner's record; clean up each owner's disposable project before its client. The owner-reported one-account CRUD check and static schema review are not independent two-user hosted RLS proof. Do not weaken policies to make verification pass.
